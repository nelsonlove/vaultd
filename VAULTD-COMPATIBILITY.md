# vaultd Obsidian Compatibility Contract

Compatibility is tiered. A higher tier never weakens the filesystem guarantees below it.

## Tier 0 — Storage compatibility

**Contract:** An unmodified stock Obsidian installation can open the vault directory. `vaultd` preserves Markdown, YAML properties, attachments, `.canvas`, `.base`, and `.obsidian` content it does not own. The filesystem is authoritative; indexes and journals are rebuildable support data.

**Current status: `vaultd` now writes, and the contract binds those writes.** Every write lands as ordinary files a stock Obsidian can open, through a temporary file in the target's own directory and an atomic same-directory rename, so a crash leaves the old bytes or the new bytes and never a torn note. The temporary name is dot-prefixed and extensionless, so it is invisible to Obsidian's own vault enumeration while it exists. A delete disposes of a file the way the caller asked: the platform trash, the vault's own `.trash/` (Obsidian's `trashOption: "local"`, a dot-directory that is never scanned, watched, or indexed), or permanent removal — defaulting to the vault's own `.obsidian/app.json` setting, and to `trash_system` (Obsidian's default) when that file is missing or unparsable. `patch_frontmatter` rewrites only the addressed span, so key order, comments, whitespace, and the body are preserved byte-for-byte. **"Span" is exact, and it is narrower than Obsidian's**, which has no such notion: `processFrontMatter` parses the YAML block, mutates the object, and re-serializes the **whole** frontmatter block, so one property edit can restyle every other property in it. `vaultd` rewrites one of three things instead. An edit addressing a top-level key splices that key's own value span (a deletion takes its whole entry line). An edit addressing a **scalar below** a top-level key — a leaf in a nested mapping, including one inside a block-style list of maps — splices that scalar's own span, so the `- ` that opens its item, that item's sibling keys, and the block indentation are not rewritten at all; a multi-line block scalar replaced by a plain scalar loses exactly the `|` and its own indented lines, and its siblings keep their bytes. Everything else below the stored granularity — a deletion, a new value that is a sequence or a mapping, a target that is itself a sequence or a mapping, a target that does not exist yet, a leaf addressed as a sequence element (`tags.0`), a leaf anywhere inside a **flow** collection (`{a: 1, b: 2}`, `[{a: 1}]`, and the same written across several lines — a `,` or a bracket ends the token there, so the value has to be quoted for flow context), or two edits under one top-level key — re-serializes the smallest enclosing **top-level property** in the addition dialect. That is the remaining reflow, and it is bounded to one property: within it, block-style collections can come back in flow style (`- {name: a, value: 9}`), indentation is normalized to the dialect's two spaces, and comments between that property's own lines are dropped. Nothing outside that one property moves, in any case, which is the guarantee Obsidian's whole-block re-serialization does not make. Two spellings exist so a host can say what `processFrontMatter` can: a `key_path` given as an array of literal segments addresses a key whose own name contains a `.` (the dot-string form reads that dot as nesting), and `set_null` writes `key: null` — the bytes Obsidian writes for `fm.key = null` — where a JSON `value: null` deletes the key. A null the **caller** sets is spelled `null`; a null the **document** already spells as a bare `key:` (the form obsidian-linter writes) stays bare, even when the property around it is re-emitted. Both read back as null, and one property can show both spellings side by side: respelling a null the author wrote is a byte `vaultd` does not own, and the churn would land in every note the linter has touched. Nothing is written into `.obsidian` except through the explicit raw `write_file`, and `--read-only` refuses every write in the process.

**One deliberate divergence, recorded rather than claimed away:** on a case-insensitive filesystem, a path that differs from an existing one only by case is refused with `case_collision` and nothing is written. Obsidian mishandles the same situation — it will happily act on a name the filesystem then folds onto a different file. `vaultd` prefers a typed refusal the caller can act on to a write that lands somewhere the caller did not name.

These claims are exactly as strong as the tests behind them: temp-then-rename atomicity, the case-collision refusal, byte fidelity outside patched spans, and containment (no traversal, no NUL, no symlink out of the vault) are each pinned by tests in `crates/vault-index` and `crates/vault-server`, and by a randomized oracle that requires a mutation and an external edit to be indistinguishable to the semantic layer.

The trash dispositions carry **one deliberate exception, stated rather than glossed**: `trash_local` and `permanent` disposal are pinned by tests (including the numbered-rather-than-clobbered second delete of the same name, and the refusal to delete inside the local trash), and the *selection* of all three modes from `.obsidian/app.json` is pinned — missing file, `"local"`, `"none"`, and a corrupt file each map to the documented mode. But `trash_system` **disposal is never executed by the suite**, by a written policy in the test files themselves: running it would put fixtures in the developer's own `~/.Trash`. So the mode a bare vault defaults to is verified to be *chosen* correctly and is not verified to *dispose* correctly. Nothing here is pinned against a *running* Obsidian: the storage-tier claims are about the filesystem, and only the Tier 1 structural shapes are capture-pinned (see below).

## Tier 1 — Semantic compatibility

**Target contract:** Match documented Obsidian behavior for wikilinks, Markdown links, aliases, headings, blocks, embeds, tags, properties, backlinks, unresolved links, and path/link resolution. Compatibility claims require fixture tests against observed Obsidian behavior.

**Current status:** the semantic read path is implemented with committed fixture coverage (`fixtures/semantic-read-path/`) for:

- frontmatter properties, aliases, and property tags with exact source spans;
- headings, block identifiers, and body tags (including nested and Unicode tags);
- Markdown links and embeds with percent-decoded targets and exact destination spans;
- wikilinks and wiki embeds with display text and heading/block subpaths;
- deterministic read-only scans, backlinks, unresolved references, and ambiguous candidates;
- structured diagnostics for malformed frontmatter, wikilinks, tags, and block identifiers;
- structural **sections** — one per top-level block, in document order, with its kind, its exact span, and the block identifier that owns it — and **list items** with exact spans, the line-number parent convention, and raw task state;
- the **vault file tree**: every non-hidden folder and file, with its kind (`note`, `file`, `folder`), byte size for files, and creation and modification timestamps in Unix milliseconds.

**How the structural shapes are pinned.** Sections and list items are pinned against *observed* Obsidian behavior at version **1.13.4**, captured at runtime through the public plugin API (`app.metadataCache.getFileCache`) against a live stock Obsidian and committed verbatim as 22 fixtures in `crates/vault-core/tests/fixtures/structural/`. Nothing is derived from Obsidian's source or `app.asar`, and nothing is inferred from the published typings alone: where the typings and the capture disagreed, the capture won. The fixtures' own README records the conventions the capture settled — that Obsidian's offsets are UTF-16 code units while `vaultd`'s spans are bytes (converted for comparison, never the reverse), the negated-start-line parent convention for top-level items with its line-0 edge case, task state as the raw bracket character, and an empty note reporting absent rather than empty collections.

Four divergences are recorded rather than claimed away: `vaultd` does not persist a block identifier on an individual list item (sections carry theirs), it does not reproduce the zero-width phantom `text`/`element` sections Obsidian can emit at end of file, it computes no content revision for a non-Markdown file, and its "hidden" rule excludes only dot-prefixed *directories* — a dot-prefixed *file* (`.DS_Store`, `.gitignore`) becomes a tree row, where stock Obsidian excludes dot-prefixed entries of either kind from its vault object model entirely. Section kinds outside the observed vocabulary pass through literally rather than being normalized, so an unknown kind survives a storage round trip.

Resolution follows the documented forms; undocumented Obsidian resolution behavior is returned as an explicit ambiguous or unresolved result rather than guessed, and no full compatibility claim is made for it.

## Tier 2 — Behavioral and interface compatibility

**Target contract:** Provide documented operations for note lookup, search, resolution, backlinks, compare-and-swap mutation, recoverable transactions, events, CLI commands, and `obsidian://` URI handling. Protocol support is declared per operation and version.

**Current status:** protocol version 1 executes `health`, `get_vault_info`, `list_notes`, `get_note`, `resolve_link`, `get_backlinks`, `list_references`, `get_diagnostics`, `refresh_index`, `subscribe_events`, and `unsubscribe` against a persistent SQLite index kept live by a filesystem watcher; the filesystem remains authoritative and the index is derived from it, never the other way round. Subscriptions deliver bounded **post-commit** events — the generation an event names is already committed and readable — and every overflow degrades into a `resync_required` marker rather than a lost change.

Compare-and-swap mutation is now implemented: `write_note`, `create_folder`, `rename_note`, `rename_folder`, `copy_file`, `delete_note`, `delete_folder`, `patch_frontmatter`, and the raw `write_file`/`read_file` pair, each with typed refusals that change nothing, preconditions checked against the bytes on disk, and a response sent only after the generation containing the write has published — so a client reads its own write at the generation it was handed. Rename repairs inbound links in that same generation, preserving each reference's spelling. Bulk reads are implemented as **snapshot sessions**: `open_snapshot`, `snapshot_tree`, `snapshot_notes`, and `close_snapshot` page a whole vault from one pinned read transaction, coherent at a single generation across the file tree and the semantic rows alike. Two per-path reads answer the same questions about a handful of paths rather than a whole vault: `get_note` takes an `include` naming the structural facets (`sections`, `list_items`), and `get_tree_entries` returns tree rows for exactly the paths a client names, reporting the rest as `absent` rather than as an error. The raw `write_file`/`read_file` pair now has a third member beside them: `read_dir` lists one directory's immediate entries — hidden folders and the configuration zones included, the empty path naming the vault root — which is the only way a client can enumerate installed plugins, since the tree index excludes hidden paths by design and `read_file` reads only regular files. `--read-only` refuses every write, the `.obsidian` zone included.

**Creating a folder inside the `.obsidian` zone is now possible**, which closes the gap earlier revisions of this document and `docs/protocol.md` recorded as the follow-up "Create folders inside the `.obsidian` zone". `create_folder` serves the configuration zone and every hidden folder as a raw create: no generation is published (the `generation` key is absent, not zero), and a `config_changed` event announces it when the folder landed inside `.obsidian/`. A plugin host can therefore make `.obsidian/plugins/<id>/` and its own configuration directory and then write into them. `delete_folder` and `rename_folder` still refuse both — making a directory is undone by removing it, while emptying `.trash/` or removing `.git/` is not — and every other containment gate on `create_folder` is unchanged, including the refusal of an ordinary-looking path that *resolves* onto an unindexable one.

Recoverable transactions, search, CLI commands beyond daemon configuration, and URI handling remain targets, not implementations — as do multi-file atomicity, conflict merging, journaling, and undo, which this milestone deliberately does not attempt.

## Tier 3 — Headless Obsidian plugin API compatibility

**Contract:** A separate Node runtime — the `vaultd-host` binary in the `host/` workspace — implements documented non-UI portions of `App`, `Vault`, `MetadataCache`, `FileManager`, `Plugin`, `Editor`, `app.plugins` and `app.internalPlugins` against `vaultd`, and runs unmodified Obsidian community plugin bundles with no Electron, no DOM and no window. Plugin compatibility is measured per plugin and per API surface, and what follows is the measurement, not the intention.

Undocumented Obsidian internals are best-effort and never part of the stable core contract.

**Parity is pinned against observed behaviour at a named version, and is never derived from Obsidian's source.** Every golden outcome below was produced by watching a **live Obsidian 1.13.4** perform the action on **2026-09-09** and committing the resulting tree verbatim; nothing was read out of `app.asar`, and no `expected/` tree was produced by running this host and blessing its output. The same rule governs Tier 1's structural fixtures, above. Where the published typings and a capture disagreed, the capture won.

### The API surface, by policy

Every symbol this host exposes carries one of five policies: **implemented** (real behaviour), **harvested** (recorded as an invokable capability rather than rendered), **safe-stub** (an inert value or a silent no-op, logged once per plugin and symbol and reported by the compatibility detector), **absent** (a typed `HeadlessUnsupported` throw) or **absent-field** (a field-shaped symbol that is simply not populated, so a plugin reading it gets `undefined` and nothing throws). Anything undeclared defaults to absent, so a gap surfaces in the compatibility report rather than as mystery breakage. **Absent-field is a separate kind rather than a note on an absent row**, added 2026-09-24: every filter in the host that means "this host refused a call" is written `policy === "absent"`, so a field that throws nothing had to stop answering to that word. The three rows are `CachedMetadata.footnotes`, `footnoteRefs` and `referenceLinks` — the frontmatter facets `vaultd` does not parse.

Measured from the shipped table at commit `8661010`: **269 declared symbols — 104 implemented, 82 safe-stub, 74 absent, 9 harvested.** (Since 2026-09-24 three of those 74 are spelled `absent_field` instead; the measurement is left as it was taken, with the delta named rather than silently restated.) 105 of the 269 are dotted members owned by their declaring module rather than names a plugin can import. `host/packages/host/test/api-policy.test.ts` holds the table to its own claims in both directions — an export with no policy and a policy with no export are both failures — and additionally checks the shape of the value behind each row, because a table can be consistently wrong.

### Golden-plugin conformance: three of eight

Eight real community bundles are committed under `host/fixtures/golden/`, each with its input vault, the bundle that ran, the tree a live Obsidian produced, and a machine-readable scenario. **Three of the eight reproduce a mutation a live Obsidian made. That is the conformance claim, and it is not five and not eight.** The other five each compare something weaker, and the reason is stated per plugin rather than folded into a total:

| plugin | version | what the suite compares | conformance? |
| --- | --- | --- | --- |
| `folder-notes` | 1.8.26-nl.5 | the whole tree, against a tree Obsidian changed (`Project/Project.md` created) | **yes** |
| `obsidian-linter` | 1.32.1-nl.1 | the whole tree, against a tree Obsidian changed (`Messy note.md` rewritten), with `created`/`modified` normalised as wall-clock | **yes** |
| `obsidian-rollover-daily-todos` | 1.2.0 | the whole tree, against a tree Obsidian changed (unfinished todos moved), date-remapped | **yes** |
| `find-replace` | 0.1.0 | an unchanged tree — both its commands only open a panel, and the replacement step is module-local | no: smoke |
| `nested-properties` | 1.6.0 | an unchanged tree — the plugin does not load at all, and the case asserts that | no: see below |
| `tag-wrangler` | 0.6.5-nl.2 | an unchanged vault, with the captured `editor-menu` excluded from the comparison | no on the menu |
| `automatic-linker` | 4.9.0 | its own input — the command runs and writes nothing | no: see below |
| `quickadd` | 2.24.2 | nothing: its `expected/` is not a capture of the action the scenario names | no |

The suite additionally asserts **which** goldens carry a real mutation and which are byte-identical, so a case cannot drift from conformance into vacuity unnoticed, and it asserts that every golden reaches **zero** absent surfaces — all eight do.

**Two limits inside the three that do conform.** `obsidian-linter`'s primary GUI write path is a CodeMirror 6 `dispatch` transaction on the live editor, which has no headless equivalent at all — no CM6 instance, no view, no state field — so its golden drives the **file** path (`vault.modify`, and the YAML `vault.process` it runs from `metadataCache.on("changed")`). A passing linter case is therefore not evidence that the editor path works. And `obsidian-rollover-daily-todos` is date-dependent: the capture's 2026-09-09 is "today", so the fixture is remapped rather than replayed verbatim.

### Three surfaces this host deliberately does not have — accepted as documented limits

Each of the three non-conformances below is a recorded design decision, not a defect, and each has a golden pinning its consequence. **Reversing any of them is a design call rather than a bug fix. The project accepted `nested-properties` on 2026-09-17 and `automatic-linker` and `tag-wrangler` on 2026-09-22 as documented limits; none is open.**

- **`automatic-linker` writes nothing, because `getActiveViewOfType(MarkdownView)` is `null` headless.** Its `format-file` body is gated on `{ file: getActiveFile(), editor: getActiveViewOfType(MarkdownView)?.editor }` and returns early unless **both** are present. The host makes the active file active and answers the view with `null` on purpose: a `MarkdownView` would satisfy `instanceof` and then promise a `previewMode` and a `getMode()` that do not exist, which is a worse lie than the null. The capture's `expected/` was produced by calling the pure transform plus `vault.modify` directly, which the fixture README states.
- **`nested-properties` does not load, because `app.metadataTypeManager`'s registered type widgets are a GUI surface this host lacks.** Its `onload` builds property-editor widgets off `registeredTypeWidgets` and asserts each is non-null; this host answers an empty map, the plugin's own assertion fires, the load is rolled back, its command is refused and the vault is unchanged. It is **not** a typed `HeadlessUnsupported` — the plugin's assertion fires before any absent symbol is reached — so nothing lands in the unsupported tally.
- **`tag-wrangler`'s context menu is empty headless, because `host.list_menu_items` has no cursor.** The host builds an editor-menu subject of a headless editor stub plus `{ file }`, and the plugin's one `editor-menu` hook needs a cursor position to know which tag it is over. The capture's six items are therefore not reproduced and the captured `editor-menu.json` is excluded from the tree comparison. Separately, and independent of the cursor: tag-wrangler's remaining surface is DOM-delegated listeners, which are structurally unreachable with no DOM and are recorded as `HarvestedUnreachable` rather than silently missing — the shipped bundle yields **17** such rows at runtime, of which **3** are `contextmenu`-typed, against the capture record's ten call sites; the difference is unexplained and is an open capture item.

### Bundle scan — information, not a claim

The compatibility detector's static scanner was run over all eight golden bundles and reported minification, a tier estimate with its reason, framework fingerprints, required Node builtins, command counts and bundle size. Those figures were **scanned on 2026-09-16**, and a plugin update would change them — so treat them as a reading of those eight bundles on that date rather than as a claim about this host. **One of them is asserted, and this document had it backwards until the final review:** `tier_estimate` is pinned exactly by two goldens through `host.compat_report` — `quickadd` at **3** (`test/golden/quickadd.test.ts`) and `tag-wrangler` at **2** (`test/golden/tag-wrangler.test.ts`) — so those two numbers are a contract and changing either fails the suite. The rest of the scan's figures — minification, framework fingerprints, required Node builtins, command counts and bundle size — have no test depending on them. They live in the Task 20 report. The two facts from that scan worth carrying here are that `nested-properties` is the only golden requiring Node builtins (`buffer`, `fs`, `os`, `util`, `zlib`), which a shipped `--dry-run` refuses by name, and that no golden requires Electron.

### What the host does not do

It writes no vault byte directly. Every shim write path funnels through a `vaultd` mutation operation, and that is proven by instrumentation rather than asserted: a filesystem write guard counts direct writes during the golden suite and the suite fails on any, and a static check bans the import form the runtime guard cannot see, with exactly two declared exempt writers (the filesystem seam and the watchdog worker), measured rather than assumed. It runs no UI: Tier 4 is unchanged. It is not a sandbox — plugins run with the host's Node privileges exactly as they do under Electron, and `--dry-run` is an evaluation tool with an enumerated intercepted-surface list, not a containment boundary.

The host's own protocol, its operations, its error codes and the full dry-run surface are in `docs/protocol-host.md`; the design and its execution-time rulings are in `docs/design/headless-plugin-host.md`; measured startup, write round trip, hydration, per-plugin load and timer cadences are in `docs/performance/headless-host-baseline.md`.

## Tier 4 — UI runtime compatibility

**Out of scope for the semantic runtime:** Workspace layout, editor behavior, CodeMirror, DOM views, Electron behavior, themes, and CSS belong to client runtimes.

## Synchronization compatibility

Sync is orthogonal to the tiers. Adapters exchange generic blobs, revisions, conflicts, and tombstones. Obsidian Sync, Git, WebDAV, or another provider must not change core semantics or filesystem authority.
