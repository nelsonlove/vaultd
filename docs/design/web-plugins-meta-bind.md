## What a view field does, in the order it does it

`onload` reads its settings with `loadData()` and calls `saveData` at once when the stored object lacks any default key. It then builds `ObsMetaBind`: a settings tab (and, in `onLayoutReady`, `settingTab.update()` plus three `vault.on` listeners), four metadata sources (frontmatter, memory, global memory, scope), a `metadataManager.cycle` on `registerInterval(window.setInterval(…, syncInterval))` (200 ms by default), one markdown post-processor with sort order 1, code-block processors for `meta-bind`, `meta-bind-js-view`, `meta-bind-embed`, `meta-bind-embed-internal-1` … `-N` and `meta-bind-button`, a CodeMirror 6 editor extension, five commands, CodeMirror 5 highlight modes (`window.CodeMirror.defineMode`, when `enableSyntaxHighlighting` is on, which is the default), a playground view, and an `editor-menu` listener. There is no `meta-bind-view` code block; a block view field is a `meta-bind` block whose content starts with `VIEW[`.

The **inline path**: the post-processor walks `el.querySelectorAll('code')` in each rendered section, skips a `code` with class `mb-none`, reads `innerText`, and asks the plugin's own API whether it is a field declaration (`INPUT[`, `VIEW[`, `BUTTON[`). For a field it creates a mountable (`createInlineFieldOfTypeFromString(type, text, ctx.sourcePath)`) and calls `wrapInMDRC(mountable, codeEl, ctx)`, which builds a `MarkdownRenderChild` on the `<code>` element itself and passes it to `ctx.addChild`. The **block path** is the same through the `meta-bind` code-block processor, after `await loadPrism()`, with the processor's `el` as the container and an `ObsNotePosition` that calls `ctx.getSectionInfo(el)` when asked.

Parsing the declaration **validates every bind target synchronously**: a target with no file part is the note itself, and both forms go through `metadataCache.getFirstLinkpathDest(path, '')`; a miss throws "file path not found", which becomes an error indicator. When the render child loads, the view field mounts: it empties the `<code>`, adds `mb-view`, builds a `div.mb-view-wrapper`, and subscribes a derived value to the metadata manager. Subscribing creates (or reuses) the manager's cache item for the note, which reads `vault.getAbstractFileByPath(path)` and `metadataCache.getFileCache(file).frontmatter` synchronously, and pushes the initial value. The compute and the re-render are `async`: a `text` field sets `innerText`, or with `renderMarkdown` awaits `MarkdownRenderer.render(app, text, wrapperEl, sourcePath, component)`; `math` evaluates with mathjs and sets `innerText`; `link` and `image` mount Svelte components. If the declaration has a write target (`VIEW[…][…]:target`), the derived value is written back to frontmatter and the next `cycle` syncs it through `fileManager.processFrontMatter`.

Three facts from this order shape the whole design. First, **link resolution and frontmatter reads are synchronous**, so the data a field needs must be in memory before the plugin runs; an on-demand read cannot be awaited in the middle. Second, **the output settles asynchronously**, so the server must wait for the plugin's promises and Svelte's microtask flush before it serialises. Third, **the metadata manager keeps a cache item per note path across renders** and refreshes it only from `metadataCache.on('changed')`, so a newer revision of a note must raise that event, exactly as Obsidian does, or the plugin keeps showing the old value.

## 2. The path

vaultd-web keeps rendering every note itself, as now. The reading-view renderer moves out of `spikes/htmx-client/server.js` into the host as one shared module (`host/packages/host/src/web/reading-view.ts`, compiled to `dist/web/`, which the server already loads from), so the web server and the screen host run the same code. The module returns the body as a list of **sections**, one per top-level block, each with its HTML (the `div.el-*` the spike emits today), its first and last source line (absolute, frontmatter included, which is what Obsidian's `getSectionInfo` counts), and for a fenced block its language and raw source. The web server joins them as it does today, so its output does not change.

On a note page, the web server asks the screen host only when some enabled screen plugin could change something, judged from what the plugins registered and never from knowledge of any one plugin's code: the screen host is ready, and either some screen plugin registered a reading-view post-processor (then every section is sent), or a section is a fence whose language some screen plugin registered a code-block processor for (the screen host reports both from its harvest). No plugin id, plugin syntax or plugin-specific selector appears in vaultd-web or the screen host (owner, 2026-10-20: stock is the rule; the earlier draft's gate on `<code>` elements was Meta Bind knowledge and is removed). The cost of sending every section is held down by the cache keyed on note revision (section 5) and measured in task 9. A note that fails the gate costs nothing. A note that passes sends `screen.render_view` with the note path, its revision (from the web's own `get_note`), the viewer, and the sections. The answer is a map from section index to new HTML, for the sections a processor changed; every other section keeps the web's bytes (E26). The request has a deadline (250 ms to start with, measured in task 9) and goes through the breaker the Style Settings client already has; on a timeout, a refusal or a breaker skip the page renders the web's own sections, which is what Obsidian shows with the plugin off (the declaration as inline code).

In the screen host, a stand-in **preview renderer** does what Obsidian's reading view does for each section, in a detached `div.markdown-preview-section` of the happy-dom document. It makes the note available first (section 3), advances the driven clock (E30), and builds one root `Component` for the render. For each section it sets the element's `innerHTML` from the section HTML; for a fenced section of a registered language it replaces the `<pre>` with a `div.block-language-<lang>` and calls that processor with `(source, el, ctx)`; then it runs every registered post-processor in sort-order with `(sectionEl, ctx)`. The context carries `sourcePath` (the note path), `frontmatter` (from the held row), `docId` (one per render), `addChild` (adds to the root component, which loads the child at once, as Obsidian does for a section that is attached), and `getSectionInfo(el)`, which walks up from `el` to its section and answers `{ text: note source, lineStart, lineEnd }` (E31). A `MutationObserver` per section records whether anything changed it.

The renderer then **settles**: it awaits a macrotask turn repeatedly (so every microtask, including Svelte's effect flush, has run) until no stand-in operation it started is in flight (`MarkdownRenderer.render` calls, on-demand reads) and two turns in a row brought no mutation, bounded by the deadline. If the sparse mirror recorded a miss during the pass (a bind target to a note it does not hold), the renderer fetches what was missed, unloads the root component, and runs the pass once more; at most two extra passes, and the third pass's result is final whatever it holds (E18). It serialises each changed section's `innerHTML`, unloads the root component (the plugin's `onUnmount` writes "unloaded" text into the field, so the order matters), and returns.

What the page receives is static markup: the plugin's own classes (`mb-view`, `mb-view-rendered`, `mb-view-inline` or `mb-view-block`, `mb-view-wrapper`, `mb-view-type-text`, `mb-view-markdown`, `interactive-child`) and its rendered content inside the `<code>` or block container, styled by the plugin's `styles.css`, which the page already loads (E8). No client script runs for a view field. Internal links inside the output are of two kinds: those from the shared renderer carry the web's `hx-get` and work as now; those a Svelte component writes (`link` fields) are plain `a.internal-link[data-href]` and need one delegated click handler in the web client, which is what Obsidian's own global link handler does for them (E22).

## 3. Note data on demand

The screen profile replaces `Mirror.empty` with a **sparse mirror** (`Mirror.onDemand`), which answers `MirrorQuery` for the notes it holds and as an absent file for every other path. It never opens a snapshot and never hydrates. It holds:

- **Rows**, keyed by path, each the `get_note` answer with `include: ["sections", "list_items"]`, so `buildCachedMetadata` builds the same `CachedMetadata` (frontmatter included) it builds from a hydrated row. A row carries its revision.
- **Entries** for held notes and their parent folders, so `vault.getAbstractFileByPath` answers a real `TFile` and `instanceof TFile` holds.
- **A resolution table**, keyed by `(linkpath, sourcePath)`, filled from vaultd's `resolve_link`. `firstLinkpathDest` answers a held path given in full (the note's own path, which is how a self-reference is validated) without a request, then the table, else `undefined`, and records the miss.

Before a render, `ensure(path, revision)` makes the note current: a held row at that revision is a hit with no vaultd request; otherwise one `get_note` loads it, and when it replaces an older row of the same path the sparse mirror raises `metadataCache` `changed` for it (after the row is in place, as Obsidian raises it after its cache moves), so the plugin's own cache item takes the new frontmatter (E19). Misses recorded during a pass are fetched between passes: each missed linkpath with one `resolve_link`, each resolved target note with one `get_note`.

Held rows are bounded: a least-recently-used cap (start at 2,000 notes, measured in task 9) evicts rows no render has used for the longest time, and an evicted path raises `vault` `delete` only if the plugin still holds a cache item for it (it does not after its own 300 idle cycles). The screen host subscribes to vaultd's events: a `generation_committed` naming a held path in `modified` drops that row's freshness (the next `ensure` refetches), one in `deleted` drops the row and raises `vault` `delete` (which unloads the plugin's mountables and cache for it), and any `created` or `deleted` path clears the resolution table, since a new or gone file can change what a name resolves to. A `resync_required` clears everything.

`metadataCache` answers for one note through the existing facade unchanged: `getFileCache` finds the row in the sparse mirror and memoizes by revision as it does now. The policy column for the screen profile reads these symbols as implemented over held notes, which also closes the startup fix's open point that the empty mirror answered silently.

## 4. renderMarkdown

The stand-in's `MarkdownRenderer.render(app, markdown, el, sourcePath, component)` produces the same reading-view markup vaultd-web produces, from the shared module of section 2, not from Obsidian's renderer and not from any plugin code. A fragment has no `get_note` answer, so the module cannot take its link spans and resolutions from one. The design adds one read-only vaultd request, `parse_fragment { source_path, text }`, which runs the same parser and resolver vaultd indexes notes with over the text and answers the `get_note` facets the renderer reads (`outgoing` with resolutions, `headings`, `blocks`, `tags`) without touching the index (owner decision 1). The stand-in then renders the fragment into `el`, runs the code-block processors and post-processors over the result with a context whose `sourcePath` is the given path and whose children go to `component` (so a field inside rendered Markdown renders too, as in Obsidian), counts itself in flight until that settles, and resolves its promise.

Answers of `parse_fragment` are cached by `(sourcePath, text)` and dropped with the resolution table (any created or deleted path). Whether Obsidian wraps a fragment's blocks in `div.el-*` sections, as it does in the reading view, is not known; the parity capture records it, and the module takes a flag (E27). If the owner rules no on decision 1, the fallback is to render the fragment with the shared module and every link unresolved, which is visibly wrong for a description that links to another note.

## 5. Caching and freshness

The web server keeps the screen host's answer per request key: `(note path, note revision, hash of the sections sent, viewer settings revision)`. The sections hash covers the renderer's version and anything else that changes the web's own HTML (the `want` anchors, an embed's depth). The screen host keeps the same key and adds what only it knows, recorded during the render: the Meta Bind bundle digest and enabled state (the task 8 machinery already tracks both), the revision of the plugin's effective `data.json`, the revision of every other note the render read through the sparse mirror, and the resolutions it used. An entry is dropped when any of those moves: a `generation_committed` that modifies or deletes a note in its read set, any created or deleted path when it used a resolution, a `config_changed` (or the 10 s re-read) for the plugin's files, or a time-dependent field. A view field's output does not depend on the theme or the colour mode, so neither is in the key.

Cost targets, measured later against Obsidian on the same notes (task 9): a note that fails the gate adds no server time; a cache hit adds under 1 ms of server time and makes no vaultd request; a miss stays under Obsidian's own time from the start of a note's reading-view render to all its view fields settled; and in every case no client script runs for view fields and nothing restyles after first paint.

## 6. Svelte and the DOM

`text` and `math` fields write the DOM directly (`innerText`, or the rendered Markdown). `link` and `image` fields mount bundled Svelte 5 components (`LinkListComponent`, `ImageGrid` with `ImageCard`), and every field with an error mounts `ErrorIndicatorComponent`. Svelte 5's client `mount` reads `document`, the `Node`, `Element` and `Text` prototypes (it takes their property getters once, at first mount) and schedules effects with `queueMicrotask`; happy-dom provides all of them, but the screen profile must expose the classes on `globalThis` as a browser does, and task 2 proves a `link` field mounts. Updates are an exported function that sets `$state`, flushed in a microtask, which the settle loop of section 2 waits for. The serialised output keeps Svelte's empty comment anchors (`<!---->`), as Obsidian's DOM does, since it is the same Svelte code in both.

Nothing needs hydration: the page never loads Svelte. What is lost is behaviour, not markup: the error indicator's click (which opens a modal listing the errors) does nothing on the web, and a `link` field's anchor needs the delegated handler of section 2 (E22). Input fields, buttons and JS view fields are out of scope for this stage; how they appear meanwhile is E24. None of this breaks server-only placement for view fields.

## 8. Edge-case log seeds for #10

- **E14 (b).** `PluginSettingTab.update()` (the Obsidian 1.13 declarative settings API, with `getSettingDefinitions`) is absent from the shim. Meta Bind calls it in `onLayoutReady`, so the callback throws. The screen profile gives a harvest no-op; the settings UI is stage 2's.
- **E15 (b).** `window.CodeMirror` (the CodeMirror 5 global with `defineMode` and `getMode`) is absent, and Meta Bind defines three modes during `onload` when `enableSyntaxHighlighting` is on (the default), so `onload` throws. A safe-stub that records the modes.
- **E16 (b).** `loadPrism` is absent and every Meta Bind code-block processor awaits it first. A stub that resolves at once: the processors replace the block, so no highlighting is needed.
- **E17 (b).** `registerMarkdownPostProcessor` and `registerMarkdownCodeBlockProcessor` are safe-stubs, `MarkdownRenderChild` is a safe-stub, and `MarkdownRenderer.render` is absent. The screen profile gets a real preview pipeline; the headless host keeps the stubs.
- **E18 (a).** Bind targets are validated synchronously through `getFirstLinkpathDest`, so a note the sparse mirror does not hold cannot be fetched in the middle of a parse. The design records the miss and renders again (at most two extra passes); a field whose target needs a third hop shows the plugin's own "not found" error.
- **E19 (a).** Meta Bind's metadata manager keeps each note's frontmatter in its own cache across renders and refreshes it only on `metadataCache` `changed`. The sparse mirror must raise `changed` when it loads a newer revision, or a page shows the old value; a parity test edits a note between two renders.
- **E20 (a).** Writes during a page view. In Obsidian a view field with a write target writes its value into frontmatter when the note is viewed, and Meta Bind saves its settings at load when a default key is missing. The screen profile refuses note writes (owner decision 2) and keeps the settings save in the `viewer` store. So a derived value the owner never opened in Obsidian is shown on the web but not stored in the note.
- **E21 (b).** `innerText =` with newlines: a browser inserts `<br>` for each line break; happy-dom is not checked and may set plain text. The capture's multi-line case decides, and a provider fix like E13's goes in if they differ.
- **E22 (a).** Behaviour that does not survive serialisation: Svelte's delegated handlers (the error indicator's click that opens the error modal) and Obsidian's global handler for `a.internal-link` (which `link` fields rely on). The web adds one delegated handler for `a.internal-link[data-href]` without `hx-get`; the error modal has no web surface until a browser stand-in exists.
- **E23 (b).** `adapter.getResourcePath` answers `app://headless/…` in the host. `image` fields put its answer in `src`, so the screen profile must answer the web's `/raw?path=` URL. Meta Bind passes the link text, not a resolved path; what Obsidian does with an unresolved name there is in the capture.
- **E24 (a).** Input fields, buttons, `meta-bind-embed` and JS view fields run through the same processors. Until their stage, inputs and buttons render as their static controls (current value shown, no effect when used), and JS view fields show the plugin's own dependency error because JS Engine is not in the screen host. Whether inert controls are acceptable meanwhile, or their sections should keep the web's bytes, is for the input-field design.
- **E25 (a).** `excludedFolders` (default `templates`) is a plain `startsWith` on the path, so `templates2/note.md` is excluded too. The server matches Obsidian because it is the plugin's own code; recorded so nobody "fixes" it in the web.
- **E26 (a).** A happy-dom parse and serialise of the web's section HTML may change bytes the plugin never touched (attribute quoting in `hx-*` attributes, void-element forms). Only sections a processor changed are sent back, so untouched markup keeps the web's bytes.
- **E27 (a).** Whether Obsidian's `MarkdownRenderer.render` wraps a fragment's blocks in `div.el-*` sections is not known; the capture records it and the shared renderer follows it.
- **E28 (a).** One live context per screen host (E6) now holds two plugins in one document. Meta Bind renders into detached elements and keeps no per-viewer state except its settings, so renders are serialised on the same queue as Style Settings applies, and a Style Settings reload does not touch Meta Bind. Per-viewer Meta Bind settings (stage 2) would need a reload per viewer, like Style Settings today.
- **E29 (b).** `window.crypto.randomUUID` must exist on the screen window (a uuid per field and per subscription); Node has it, happy-dom's window is not checked. The bundled seedrandom requires `crypto` inside a `try`; the intercept's answer for that builtin in the screen profile is not checked.
- **E30 (a).** The metadata manager's `cycle` runs on the driven clock, which only an apply moves today. Without advancing it, idle cache items are never deleted (memory grows with notes viewed) and a dirty item never syncs (which E20 refuses anyway). The preview renderer advances the clock by the real time since its last advance before each render.
- **E31 (a).** Meta Bind calls `ctx.getSectionInfo(el)` with a code-block processor's `el`, which is a child of the section, not the section. The stand-in walks up to the section; whether Obsidian answers for a child element or answers `null` is in the capture.

## Owner decisions

1. **A read-only `parse_fragment` request in vaultd, and the reading-view renderer moved into the host as one shared module.** `renderMarkdown` must resolve links in a fragment the way the index does, and only vaultd's parser and resolver can do that without a second parser in the host. Yes: one new read in vaultd (no index change) and the renderer becomes a host module both processes use. No: fragment links render unresolved, so a description that links to another note shows a dead link. Pick: yes.
2. **A page view never writes a note.** In Obsidian a view field with a write target stores its derived value when the note is shown. Yes: the screen profile refuses every note write and records the hit; the field still shows its value, and the value reaches the note only when the owner opens it in Obsidian (or when input fields arrive, with sign-in). No: the web writes on view, so any viewer who opens a page changes the vault and wakes Obsidian Sync. Pick: yes.
