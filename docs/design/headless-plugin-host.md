## Summary

The host is a Node daemon that runs unmodified Obsidian community plugins with no Electron, no DOM, and no window. It supervises `vaultd` as a child engine process, keeps a local mirror of the vault tree and semantic state (hydrated by snapshot sessions, kept current by `subscribe_events` and mutation responses), and loads plugin bundles against a shim that impersonates the Obsidian API. Plugins' registered commands, menu items, protocol handlers, and settings become machine-readable capabilities any client can list and invoke over the host's socket.

The measured thesis: plugins break headless on missing lifecycle gates and missing API surface, not missing pixels — and the failure mode is silent. The host's hardest jobs are a faithful startup sequence and an honest four-way policy for every API symbol: implemented, harvested, safely-stubbed, or loudly absent. The registration harvest is the payoff: plugins already declare their user flows through `addCommand`, menu events, protocol handlers, and settings; the host records these instead of rendering them.

Deployment shape: the host is the daemon you install and talk to. `vaultd` speaks single-peer stdio; the host is that peer. The host's Unix socket accepts many concurrent clients and multiplexes them — vault operations forwarded to `vaultd`, plugin operations answered locally. Running `vaultd` directly (no host) remains a supported deployment; a second host against the same vault fails cleanly because its spawned `vaultd` loses the writer lease (`IndexInUse`) — the multi-host story is the lease story, now stated.

## Goals

1. Run tier-1 plugins unmodified and correctly against fixture vaults: folder-notes, obsidian-linter, automatic-linker, rollover-daily-todos, find-replace, nested-properties, and QuickAdd's execution path. (Rollover forced a real widening: it reads `app.plugins` and `internalPlugins` — see the shim section; the v1 draft would have killed its own flagship at load.)
2. Registration harvest as capabilities: `list_commands` / `invoke_command` / `list_menu_items` / `invoke_menu_item` / `list_protocol_handlers` / `invoke_protocol` (`obsidian://` handlers are an external-trigger surface five plugins publish). Tag-wrangler — zero commands, all menus — is the harvest's acceptance case.
3. A faithful lifecycle (exact sequence below), because that is where plugins silently die.
4. Single-writer discipline, enforced not asserted: every shim write path funnels through `vaultd` mutation ops, and a test proves the host process opens no vault file for writing (fs instrumentation in the golden suite).
5. Read-your-writes inside plugin code, with the ordering defined (not hoped): a shim write resolves only after the `vaultd` response arrives AND the mirror has applied that response's generation and change set. The mirror is response-driven for your own writes; the later `generation_committed` event is skipped idempotently by generation. A plugin that writes then reads through `MetadataCache` sees its own effect, and a test pins it through the shim (not just at the wire).
6. Config machinery with the write-safety half designed: `get_plugin_config` serves values plus schema (ladder below) with secret-shaped keys redacted by default; `set_plugin_config` refuses keys classified as runtime state. Classification sources: the schema ladder plus a per-plugin state/secret key registry seeded from the research's config census (**OPEN:** registry format and where it lives; draft: a data file in the host repo, PR-able per plugin).
7. The compatibility detector: bundle scanner (property-position census, lifecycle gates, framework fingerprints, tier estimate) plus a runtime harness mode recording every API call and throw. Ships with tests (fixture bundles with known ground truth) — review caught that v1 gave it a Goals bullet and zero Testing lines.
8. Interaction brokerage, honestly scoped: structural interception covers the `SuggestModal`/`FuzzySuggestModal` family (template-method classes where the base owns rendering and subclasses supply items/choice) and the shim's own prompt primitives. Bespoke `Modal.onOpen()` UIs are NOT structurally interceptable (the research's QuickAdd `plugin.api` finding is the proof) — they throw typed `HeadlessUnsupported` and are per-plugin-adapter territory, later. When an interactive client has attached as the session's interaction handler, brokered prompts route to it; a handler that disconnects or exceeds a timeout (**OPEN:** value; draft 120 s) fails the prompt with a typed error rather than hanging the plugin forever.

## Non-goals

- Tier-4 plugins, rendering, CodeMirror, real DOM.
- Plugin sandboxing. Plugins run with the host's Node privileges, as they do under Electron. Dry-run (below) is an evaluation tool, not a sandbox, and the spec no longer calls it a mitigation for what it does not mitigate.
- The Obsidian accelerator, WASM-in-vaultd plugins, and per-plugin adapters beyond the exemplar set named in Testing.
- backlink-cache as a hosted plugin — per the research's explicit verdict it is a spec to read, not a plugin to host; the mirror's backlink answers come from `vaultd` natively.
- Settings-editing UI (clients build editors over the config ops).
- Multi-vault.
- A socket transport inside `vaultd` (the host multiplexes; deferred).

## Architecture

A `host/` workspace in the vaultd repo, TypeScript on Node LTS. Components: **Supervisor** (spawns/restarts `vaultd`, owns its stdio; host death closes stdio and `vaultd` exits — lifecycle stated in both directions. **Amended by the socket transport phase:** that holds under `engine: "spawn"`, where the daemon has no listener. Under `engine: "auto"` a daemon the host spawned is spawned with `--listen` so other clients can share it, which means closing its stdin no longer ends it; the host sends it `SIGTERM` at its own shutdown unless `leave_engine_running` is set, and a daemon the host merely connected to is never the host's to end. See `docs/design/vaultd-socket-transport.md`.), **Mirror**, **Shim**, **Plugin runtime**, **Host protocol server**, **Detector**.

**Module interception:** all sampled bundles are esbuild CJS calling `require("obsidian")`; the host provides the shim via normal Node resolution (a real `obsidian` package in the host's module path) with a `Module._load` patch as the fallback for exotic loaders. No `vm.createContext`. The same patch provides `require("electron")` — a stub whose `shell.openPath`/`showItemInFolder`/`openExternal` bridge to the OS `open` command and whose `ipcRenderer` is inert (three census plugins import it; stashpad's Finder-reveal is real functionality worth bridging). Plugin load order follows Obsidian's (manifest order); there is no "dependency-safe order" to compute — plugins do not `require` each other; cross-plugin access happens at runtime via `app.plugins.getPlugin`, which returns `null` for not-yet-loaded plugins exactly as real Obsidian does, and plugins already defend against it.

**Host protocol server:** Unix socket created with mode `0600` and a peer-UID check on accept (same-UID only) — the trust model is "processes running as the user", stated; the research's TaskNotes-open-port finding is the cautionary precedent, not a pattern to repeat. JSON per line; per-client subscription registry with the same bounded-queue/drop-marker discipline `vaultd`'s own registry uses; a late-joining client receives the current generation in its hello and resyncs from it (**OPEN:** whether the host serves snapshot pages from its mirror so clients need not reach `vaultd` at all; draft: yes, mirror-served). Wire shapes for `host.*` ops are pinned in an appendix-level section of the implementation plan, not left to invention.

**Watchdog:** a `worker_threads` watchdog observing a `SharedArrayBuffer` heartbeat the main loop stamps when idle; the worker reports a wedged main thread out-of-band (its own socket connection is independent). Named mechanism because the obvious one (`postMessage`) structurally cannot report the only failure it exists to catch. Report-only.

## The shim, sized by the corrected census

Four-way policy, replacing v1's throw-or-implement dichotomy: **implemented** (real behavior), **harvested** (recorded as capability, no rendering), **safe-stub** (silent no-op or inert value, logged once per plugin+symbol, reported by the detector), **absent** (typed `HeadlessUnsupported` throw). The census's "no-oppable" classifications map to safe-stub; everything unlisted defaults to absent-throws so gaps surface in the compatibility report rather than as mystery breakage. **A fifth kind was added on 2026-09-24**, after the final review found `absent` meant two things: **absent-field**, for a field-shaped symbol that is never called and is simply not populated — the three `CachedMetadata` facets `vaultd` does not parse. It reads `undefined` and throws nothing, so it must not answer to the `policy === "absent"` filter every refusal count in the host is written with.

Implemented: `Vault` (read/cachedRead/getFiles/getMarkdownFiles/getAbstractFileByPath/getFolderByPath/getAllLoadedFiles/create/createFolder/modify/process — host-serialized per path over the CAS loop —/delete/trash/rename/copy, `on(create|modify|delete|rename)`, `adapter` subset: read via `read_file`, write via `write_file`, exists/basePath from the mirror, `getConfig` with the named load-bearing keys, `attachmentFolderPath` first); `MetadataCache` (`getFileCache` → Obsidian-shaped `CachedMetadata`, `getFirstLinkpathDest`, `resolvedLinks`/`unresolvedLinks`, `getBacklinksForFile`, **`getAllTags`**, `on(changed|resolve|resolved)`); `FileManager` (`processFrontMatter` → `patch_frontmatter` with dot-paths, `renameFile` → `rename_note`, `generateMarkdownLink`); real `TFile`/`TFolder`/`TAbstractFile`; `Plugin` base (`addCommand`, `registerEvent`, `registerInterval` — real, but instrumented: per-plugin timer registry with cadence reported in `host_info`, because the idle-cost census showed 5 Hz-forever timers exist —, `loadData` → `read_file`, `saveData` → `write_file`, `registerObsidianProtocolHandler` — harvested AND invokable); **`app.plugins`** (`getPlugin`/`plugins`/`enabledPlugins` over the host's own registry — the 21-of-56 cross-plugin surface v1 omitted; the 8-plugin `this.api` pattern works through it for co-hosted plugins) and **`app.internalPlugins`** (a registry reporting core plugins disabled, except: `daily-notes` and `templates` expose their real config read from `.obsidian/daily-notes.json`/`templates.json` via `read_file`, because rollover-daily-todos consumes exactly that; other core plugins **OPEN** as demanded); a minimal `Editor` for `editorCallback` (in scope, unchanged); `Notice` → log + host event; `Platform` desktop; `moment` (bundled; locale fixed `en` — **OPEN** if it ever matters); `normalizePath`, `parseYaml`/`stringifyYaml`, `requestUrl` over real HTTP; **`window.require`/`module`/`exports` provisioning** for QuickAdd's `new Function("require", "module", "exports", src)` user scripts — the scripts are Node-native (research surprise #3) and receive the host's patched `require`.

Harvested: `addSettingTab` (+ `getSettingDefinitions()` when present), `addRibbonIcon`, `addStatusBarItem`, `workspace.on(file-menu|editor-menu)`.

Safe-stub: `registerView`/`registerEditorExtension`/`registerMarkdownPostProcessor`/`registerMarkdownCodeBlockProcessor` (accepted, discarded, never throw — they run in `onload`), `getResourcePath` (inert URL), leaf/layout surfaces (`getLeaf` → inert leaf recording `openFile` intent, iteration → empty arrays, never undefined), `getActiveViewOfType` → null, DOM stubs (hand-rolled chain-swallowing `createEl` family, inert `activeDocument`/`window` globals), `app.setting`, `setIcon`.

### The `sections`/`listItems` dependency — a named cross-phase requirement

Review proved by grep what the census never measured: `CachedMetadata.sections` and `.listItems` are read for load-bearing logic by tasknotes and breadcrumbs, and `vault-core` stores neither. The mirror cannot fake structural parse data it does not have. **This spec requires vault-core to extend its parse output with `sections` and `listItems` rows (mdast already walks the needed structure; spans exist)** — added to the mutation phase's scope or as a small standalone task before host implementation begins (**OPEN:** which; draft: standalone pre-task, it touches only the parse/persist path). `getFileCache` parity fixtures then cover both fields, plus `frontmatterLinks` with `field.N` keys and positioned `links`/`embeds` (evidence restored to the research note's census corrections).

## Lifecycle, exactly

1. Supervisor starts `vaultd`; the mirror hydrates via a snapshot session (tree + semantic rows) at generation G.
2. The enabled set is computed (below); bundles load; `onload` runs sequentially in manifest order. `layoutReady` is false; registrations harvest as they occur.
3. `layoutReady` flips true; queued `onLayoutReady` callbacks fire in registration order. A plugin enabled later, while ready, gets its callback invoked immediately — real Obsidian's documented behavior.
4. `metadataCache` fires `resolve` per note then `resolved`. Thereafter `resolved` re-fires after every mirror update batch completes — matching Obsidian's repeating semantics — so a plugin enabled late converges on the next batch rather than deadlocking (**OPEN:** additionally fire one synthetic `resolved` to a late-enabled plugin immediately, so gate-waiting plugins need not wait for vault activity? Draft: yes).
5. Steady state: `vaultd` events → mirror → shim events, serialized on the one JS thread. Plugin writes: response-driven mirror update then resolve (Goal 5); the event re-entry is generation-deduplicated.

`vaultd` restart (host survives): mirror re-hydrates at G'; running plugins are NOT reloaded; the host synthesizes `changed` events for every path whose revision differs G→G' (a bounded diff of two mirror states) and a `resolved` after — the same shape as a bulk external edit, which plugins already tolerate. Full plugin reload on restart is **OPEN** as a config knob; draft default: no reload.

Shutdown: `onunload` with bounded timeout, intervals cleared, stdio closed, exit.

## Co-existence with GUI Obsidian

Invariant unchanged: a plugin is enabled in exactly one runtime, by configuration. Mechanics now specified: the host's enabled set lives in `.obsidian/headless-plugins.json` (**OPEN:** location stands), read and written via the phase-5 zone ops. The GUI-overlap check reads `community-plugins.json` via `read_file` — the data path exists now — at host startup AND at every `host.enable_plugin` call (point-in-time both; `.obsidian` is unwatched, so mid-session GUI changes are caught at the next host op or restart — stated limitation, with `host_info` surfacing both lists and flagging overlap whenever refreshed. **OPEN:** a slow poll on `community-plugins.json` to close the mid-session window; draft: 60 s poll, it is one small file). `--force-shared` requires naming plugins individually and prints what makes double-running dangerous (event double-fire; port binding — three census plugins bind servers at load).

## Plugin management

In-phase: enable/disable/list/config (+ the overlap check above). Install/update deferred (unchanged), with one addition from review: the on-disk layout decisions install would make are pinned NOW in the implementation plan (standard `.obsidian/plugins/<id>/` layout, nothing bespoke) so enable/disable need no later migration.

## Dry-run

Scope stated as an explicit intercepted-surface list: vault writes (recorded, not forwarded), plugin-config writes (recorded), `requestUrl` (refused with typed error by default; `--dry-run-allow-network` opts back in), `Notice`/log (recorded), OS-bridge calls from the electron stub (refused). Not intercepted: CPU, timers, reads. Dry-run is the detector's runtime-harness backend and an evaluation tool; it is not a sandbox and the text says so.

## Failure handling

- Handler exceptions: caught at the shim boundary, attributed, surfaced; quarantine at a stated threshold (**OPEN:** value; draft 5 failures in 60 s). Quarantine unloads the plugin, REMOVES its harvested capabilities, and `invoke_command` on them returns typed `plugin_quarantined` — review asked what happens to the harvest; now answered.
- Wedged main thread: watchdog reports (mechanism above); no interruption.
- `vaultd` crash: supervisor restart + the restart-continuity story above; `resync_required` propagates to host clients.
- Host crash: `vaultd` exits with it; in-flight writes either committed or never happened (phase-5 single-file atomicity); a supervisor restart replays startup.

## Testing

- **Lifecycle conformance:** startup order, gate firing, late-enable semantics (layoutReady immediate; resolved re-fire), the folder-notes `layoutReady`/`tabManager` trap, the `on('resolved')` deadlock class, restart-continuity synthesis.
- **Golden-plugin suite:** the tier-1 list against fixture vaults, byte-level outcomes vs real-Obsidian captures; runs with fs instrumentation proving zero direct vault writes by the host process (Goal 4's enforcement).
- **CachedMetadata parity:** field-by-field vs real-Obsidian captures, explicitly including `sections`, `listItems`, `frontmatterLinks`, positioned links/embeds.
- **Harvest fixtures:** tag-wrangler menus; QuickAdd non-interactive choices incl. a user script exercising `window.require`; protocol-handler invocation; brokered `SuggestModal` round-trip incl. handler-timeout and handler-disconnect; a bespoke-Modal plugin failing typed.
- **Config safety:** state-key write refusal; secret redaction; schema ladder per rung incl. a `getSettingDefinitions()` plugin, a descriptor-array plugin, and the degenerate-implementation trap (tasknotes' opaque render item must be detected as non-declarative).
- **Detector:** fixture bundles with known census ground truth; scanner output matches; harness mode's recorded-call log matches a scripted plugin.
- **Co-existence:** overlap refusal, `--force-shared` admission, mid-session GUI-enable caught at next op/poll.
- **Socket security:** non-owner-UID connection refused; socket file mode asserted.
- Determinism discipline unchanged: rendezvous over sleeps, 10x flake runs.

## Instrumentation and targets

Per-plugin load time, handler time, failure counts, timer registry with cadences, mirror hydration time, plugin-write round-trip. Baselines, not contracts: host cold start (mirror + 10 plugins, 10k fixture) < 2 s; plugin write round-trip (shim modify → resolved with mirror applied) p50 < 50 ms; golden suite green 3 consecutive runs.

## Schema ladder — where each rung lives

(Review: v1 promised the ladder and housed it nowhere.) Rungs 1–3 (`getSettingDefinitions()`, descriptor arrays, typed-interface extraction from known source) are Detector functionality producing cached schema files in the host's data dir; rung 4 (LLM introspection) is an OFFLINE tool — invoked explicitly, never at runtime — that emits the same cached schema format, so runtime behavior is deterministic regardless of rung. `get_plugin_config`'s `schema` field serves the cached artifact with a `source: definitions|descriptors|types|llm|none` tag.

## Deferred follow-on

Accelerator, WASM-in-vaultd (breadcrumbs' engine as exemplar), curated per-plugin adapters, `vaultd` socket transport, install/update flows, sandboxing, the build-time compatibility database.

## Rulings (2026-08-30) — supersedes every inline OPEN above

Inline **OPEN** markers are retained as a record of what was undecided; where this section conflicts with one, this section wins. (N) = the maintainer's call, (A) = agent's call within delegated scope.

1. **The host gets its own Obsidian config directory — not a bespoke file (N).** Instead of `.obsidian/headless-plugins.json`, the host runs against its own vault-relative config dir (default `.obsidian-headless/`) with the **standard Obsidian layout**: an ordinary `community-plugins.json`, an ordinary `plugins/<id>/` tree. Evidence this is idiomatic rather than a hack: `app.vault.configDir` is a real runtime API that 10+ installed plugins already read instead of hardcoding `.obsidian`, and Obsidian itself supports overriding the config folder per installation (stored machine-locally, outside the vault — which is exactly the "one config dir per client/machine" property). Consequences: no invented format; install/update flows become the same operation in a different directory; the shim reports the host's dir from `configDir` and those 10+ plugins do the right thing with no special-casing; and plugin data isolation becomes **structural** — the host's plugins write their own `data.json` in their own tree, so the GUI-clobber hazard cannot occur rather than being prevented by convention. A plugin may therefore run headless with different settings than its GUI copy, deliberately.
2. **Plugin binaries: the host keeps its own copies, excluded from backup (N).** The host's `plugins/<id>/` holds its own `main.js`/`manifest.json`. Fully independent, ordinary file writes for install/update, headless-only version pinning possible. Cost accepted: ~28 MB duplicated on disk, deliberate version-drift management, and **a required ignore rule so the vault backup repo does not commit a second copy of every bundle on every update** (the backup already tracks 2,567 files under `.obsidian`). That ignore rule is an action item, not an implementation detail — it belongs in the same pass as the secret-key ignore rules already filed in the 00.00 inbox note.
3. **The GUI-overlap invariant survives the config-dir split, and gets cleaner (N+A).** Separate config dirs make the enabled sets independent; they do **not** prevent enabling the same plugin in both, and the double-fire consequence is unchanged (two folder notes per folder, two lint passes). The check becomes a comparison of two ordinary `community-plugins.json` files — the host's own and Obsidian's — read via `read_file`. Checked at host startup, at every `host.enable_plugin`, and on a 60 s poll of Obsidian's file to close the mid-session window (A).
4. **Core plugins: two reimplemented as config readers, six reported absent (N, from measured demand).** Grepping all 56 bundles for real `getPluginById`/`internalPlugins` usage found exactly eight referenced, and what they consume is overwhelmingly *config Obsidian already wrote to disk*, not behavior. Core plugins are compiled into `app.asar` and closed-source, so any support is reimplementation — but at this scope that means parsing JSON, not rebuilding features.
   - **Reimplement:** `daily-notes` (7 consumers: governor, homepage, nldates, importer, rollover, brat, tasknotes — folder/format/template from `.obsidian/daily-notes.json`) and `bookmarks` (3 consumers: fileclass, governor, recent-files — the tree from `.obsidian/bookmarks.json` plus a small read API).
   - **Report absent:** `file-explorer` (folder-notes and pane-relief want leaf handles for CSS; research confirmed folder-notes self-disables cleanly when the leaf list is empty), `global-search` (tag-wrangler triggers a search; vaultd has no search yet, so that menu item degrades honestly; **amended by the search phase:** `global-search` is no longer absent — it has a real instance with the two methods tag-wrangler calls, `getGlobalSearchQuery` and `openGlobalSearch`, served when `core-plugins.json` enables it; see `docs/protocol-host.md`, **Search**), `bases`, `file-recovery`, `properties` (all advanced-canvas, itself UI-tier), `workspaces` (governor listing; opening one is meaningless headless).
   - Note: `daily-notes` is `false` in this vault's `core-plugins.json` today, yet seven plugins reference it — they already cope with it being disabled, so reporting it disabled-but-configured *is* the status quo.
5. **The host serves snapshot pages to its own clients from the mirror (A).** Clients need one connection, not two; the mirror already holds the data, so serving from memory beats proxying; and it preserves the single-door property. `vaultd`'s own snapshot ops remain available to anyone talking to it directly.
6. **A plugin enabled after startup receives a synthetic `resolved` immediately (A).** The alternative — waiting for the next real vault change — is never, on a quiet vault, which is precisely the silent-deadlock class the research identified for the six gate-waiting plugins. Firing immediately after that plugin's `onload` and `layoutReady` reproduces what it would have experienced at boot.
7. **An engine restart does not reload plugins (A), with a config knob to force it.** Reloading discards plugin in-memory state and re-runs `onload` side effects; synthesizing `changed` events for every path whose revision differs across the restart looks exactly like a bulk external edit, which plugins already tolerate.
8. **Remaining calibration (A), all config fields so none needs a protocol change:** brokered-prompt timeout 120 s (then typed failure, never an indefinite hang); quarantine at 5 handler failures in a rolling 60 s; state/secret key registry as a JSON data file in the host repo keyed by plugin id with `state_keys` and `secret_keys` arrays, seeded from the research's config census and PR-able per plugin; `moment` locale fixed to `en`.

## Corrections from plan drafting (2026-08-30)

Writing the implementation plan against the real bundles surfaced three things the spec got wrong or left implicit. These supersede the text above.

9. **`templates` is absent, not reimplemented.** The Architecture section's shim paragraph named `daily-notes` *and* `templates` as config readers; Ruling 4 named `daily-notes` and `bookmarks`, leaving `templates` in neither list. Ruling 4 is the evidence-based one and wins: the demand grep over all 56 bundles found `templates` referenced by **nothing**. It takes the generic default — real `enabled` state from `core-plugins.json`, `instance: null` — and quickadd and folder-notes hit their existing degraded branches, as they already do for any disabled core plugin.

10. **The mirror must hold a position index, and `getFileCache` warms asynchronously.** A gap none of the six spec reviewers caught: Obsidian's `CachedMetadata` positions are `{ line, col, offset }`, but vaultd stores **byte offsets only**, and converting between them requires knowing where the line breaks are — which requires the body the mirror deliberately does not hold. Resolution: the mirror maintains a compact per-note position index (line starts plus non-ASCII character triples, on the order of 8 bytes per line), warmed asynchronously after hydration. `getFileCache` returns `null` for a note whose index is not yet warm — which is Obsidian's own documented contract for an unindexed file, so plugins already handle it — and the lifecycle's `resolved` fires only after warm-up completes, so the six gate-waiting plugins never observe a half-warm cache. This makes the "mirror holds no bodies" decision survivable rather than quietly wrong.

11. **Tag-wrangler is a weaker harvest case than claimed, and the taxonomy needs a fourth outcome.** Ground truth from the shipped bundle: zero `addCommand`, zero `file-menu` registrations, **one** `editor-menu` hook, and the rest of its surface wired through ten DOM-delegated listeners (two `contextmenu`-typed; the others pointerdown/drag/mouseover/click) plus a `Menu.prototype` patch for preview-mode tags. Those ten are structurally unreachable with no DOM — they are not registered through any Obsidian API the host can intercept. So the harvest recovers one item, not eleven. Two consequences: the shim gains a **`HarvestedUnreachable`** classification (a capability the plugin has but that no headless client can invoke, reported in the compatibility record rather than silently missing), and the acceptance test asserts the honest number instead of a hoped-for one. The broader claim that registration harvesting rescues tier-2 plugins survives, but narrows: it rescues plugins that register through Obsidian's menu API, and does nothing for plugins that attach their own DOM listeners. Tag-wrangler turns out to be the second kind.

Two smaller plan-level calls, recorded so they are not rediscovered: config files resolve host-dir-first with a fallback to `.obsidian/` (a fresh headless config dir therefore inherits the real settings, which is what makes rollover work on day one, while an explicit override wins); and a peer-UID check has no portable Node API without a native addon, so socket access control is enforced by a `0700` directory plus a `0600` socket plus an ownership nonce — the same admitted process set, with the true cross-UID test documented as a `sudo`-gated manual check rather than pretended in CI.

## Rulings (2026-09-22) — made during execution

Everything above this line was written before implementation. These are the amendments the implementation plan took while phase 6 was built, each recorded at the time in `docs/plans/headless-plugin-host-implementation.md` as an `Amended` note and in the ledger as a `Ruling:` line. They are listed here so the design and the shipped host can be read against each other without opening the plan. They do not reopen doctrine; each is a decision already made, with the file that holds its detail named.

12. **Cache events group with their own file's vault event (2026-09-15, Task 15).** The lifecycle section above says the mirror's events become shim events and says nothing about their order within a batch. The plan originally grouped every `metadataCache` event after every `vault` event; the ruling is the shipped per-file grouping — create; modify with its `changed`; rename; delete with its `deleted`; then one `resolved` for the batch. Reason: Obsidian's documented model is per-file, and the brief's stated reason (one event per move) is satisfied either way. Pinned by `lifecycle-order.test.ts` → "groups each file's cache event with its own vault event".

13. **The late server operations are wired per service, not all at once (2026-09-16, Task 18).** Six operations need services that do not exist when the server is built — the interaction broker, the plugin-config service, and the detector. `HostServerWiring` is a partial that `attachWiring` merges, and each late operation answers `host_not_ready` naming **its own** missing service rather than a blanket refusal. Task 18 wired the three interaction operations and the `host.interaction_request` event; Task 20b attached `{ pluginConfig, detector }`. Two smaller calls in the same ruling: there is no `shim/modals.ts` — `Modal`, `SuggestModal` and `FuzzySuggestModal` already live in `shim/components.ts`, so `open()` changed in place — and `SuggestModal.open()` returns a promise that never surfaces an unhandled rejection, because real plugins do not await it.

14. **A collapsed prompt delivery fails the prompt at once (2026-09-16, carried from the Task 18 review).** A brokered prompt's `host.interaction_request` rides the attached client's subscription queue, so a client that has fallen behind can have the request collapsed into `subscriber_lag` / `resync_required` — and attaching subscribes that client to the whole event stream, which makes it the likeliest client to lag. Delivery now reports whether every subscription took the line, and a prompt whose delivery was collapsed fails immediately with `interaction_unavailable` instead of waiting out `promptTimeoutMs`. The durable half — a client treating `resync_required` as "re-ask what is pending" — is backed by `host.list_interactions`, which returns the broker's `pending()` rows and shipped at Task 20b.

15. **Dry-run gained an overlay, because a dry run has to compose (2026-09-16, Task 19b).** The Dry-run section above describes what is intercepted and stops there. The Task 19 review measured the consequence: under `--dry-run` a plugin that created a note and then used it threw "the mirror has no row for it", and `modify` then `read` returned the old bytes, because nothing was written and the mirror never moved. That breaks "the plugin sees success" and would have made the Task 20 detector verdict any daily-notes-shaped plugin `fails` for a harness defect. The ruling added a **dry-run overlay** held by the write gate: the paths it synthesised and the last bytes it recorded, consulted by the vault index and the read paths **only after the mirror answers `null`**, with precedence *removed, then overlay bytes, then mirror metadata*. **No synthetic rows go into the `Mirror`** — it mirrors the daemon, and a resync would fight them. Dry-run is not read isolation either: a change somebody else makes still reaches the mirror. Two further calls at the same review: the host's non-`host.` client proxy routes through the write gate (a dry run that forwards a client's `write_note` is a dry run that writes), and synthetic answers follow the daemon's dot-segment rule for `semantic` and `generation` presence while `kind` keeps the config-dir rule. The whole surface is enumerated in `docs/protocol-host.md`'s **Dry-run** section.

16. **Five rulings on the compatibility detector (2026-09-16, Task 20 reviews).** (1) The runtime harness runs inside the host's **own** dry-run assembly by windowing the existing gate and recorder — "a fresh gate and recorder" means windowing, not a second assembly — and it requires `--dry-run`, refusing otherwise with the typed `detector_requires_dry_run`. (2) A probe must leave the host as it found it: the restore is decided from the enabled **set** read before the load, the probe's own gate rows are dropped by identity (tagged at record time), never by position, and a probe-caused load failure is recorded visibly but never counts toward the quarantine window — five reports in a minute must not quarantine a plugin no user action touched. (3) The verdict enum gains a fourth value: `runs | degrades | fails | unknown`, where `unknown` means a harness was attempted and refused, and the row carries `harnessAttempted` so a client can tell which kind of null a null harness is. (4) The event bus attributes each handler run to the **listener's** plugin, which also corrected quarantine attribution. (5) `ScanResult` separates generic-member hits (`genericSymbols`) from `apiSymbols`, so the specific surface reads as the specific surface.

17. **Plugin configuration froze a wire shape and two throws (2026-09-16, Task 17).** Goal 6 above names the schema ladder and the refusal but not the shapes. As shipped: `redacted_keys` is `(string | number)[][]` — segment arrays, following the daemon's `patch_frontmatter` `key_path` precedent, where numbers are array indices — and a depth-located refusal row carries `path` beside its top-level `key`. There are **four** refusal reasons, not three: `state_key`, `unknown_key`, `type_mismatch`, and `redacted_value` (a client storing the literal string `[redacted]` learns why). Redaction applies at every depth, in objects and arrays, and stays populated across a reveal. Both walks carry a depth budget of 64 and fail closed; `plugin_data_too_large` and `plugin_data_too_deep` are **throws mapped to error responses**, never refusal rows, because neither can be attributed to one key and neither writes anything. `set` and `Plugin.saveData` both run inside the dispatch queue's per-path exclusive lock, so the queue is the lock. The round trip preserves keys and values under JSON semantics and is not byte-lossless: integers past 2^53, number spellings, indentation and the trailing newline are normalised.

18. **One copy of the wiring, and an ordered shutdown (2026-09-22, Task 22a).** The binary and the test harness had two copies of the startup order, and only one of them could ship — four mutations of the binary's copy (the watchdog never started, `allowNodeBuiltins` forced true, the user-script globals never provisioned, the shutdown order reversed) survived the whole suite, because the copy under test was the harness's. `src/host.ts`'s `startHost` is now the single copy, which `main.ts` and the live-host seam both drive. Its `stop()` is **ordered, and that is a correctness property rather than tidiness**: plugins unloaded, the dispatch queue drained within a bounded budget, the socket closed, the mirror stopped, the watchdog joined, and only then the process-wide globals restored — because a plugin parked on `window.setTimeout` that wakes into a process with no `window` throws onto a promise nobody holds, and Node's default for that is to kill the process. The binary's exit 4 is decided from the coexistence monitor's **typed** overlap report, never from the text of a failure message. The residue is stated rather than guarded: work outliving the drain budget runs on after the globals are back and can still turn a clean shutdown into exit 1.

19. **A mutation that could not read its write back refuses, and says so with the typed error (2026-09-24, follow-up round).** `Mirror.applyMutation`'s promise is what makes read-your-writes true inside plugin code, and two roads out of the apply returned without having applied anything: `applyChangeSet` catches an `EngineLostError` out of its refetch and `runResync` catches one out of a re-hydration, both reading it as "a `runtime_recovered` marker is on its way". That is right for an **event**, whose caller is a fan-out nobody holds, and wrong for a **mutation**, whose caller is a shim write still in progress. `Vault.create` took the quiet return for a success and threw `the daemon accepted a write to X but the mirror has no row for it` — the intermittent failure the 22a implementer saw twice and neither reviewer reproduced in ten serial golden runs each, because it needs the engine to be replaced in the window between the daemon answering a write and this host refetching it. `applyMutation` now asserts its own contract on the way out: if `appliedThrough` has not reached the acknowledged generation, nothing applied it, and the promise rejects with `EngineLostError` — the write landed, this host could not read it back, and the replacement engine will re-hydrate. `appliedThrough` is the exact witness because every road that really applied the generation advances it and no road that abandoned the work does. Pinned deterministically in `test/mirror-engine-lost.test.ts` by taking the engine away between the write's request and its response. **The blast radius, measured by the round's review and closed with it.** Making a mutation refuse means every write road can reject where most of them used to resolve, and real plugins call `app.vault.modify(file, text)` with no `await`: the reviewer's first full-suite run floated `the engine was replaced before the mirror could read back the write at generation 3` out of `obsidian-rollover-daily-todos` and through `golden.test.ts`'s own unhandled-rejection guard, exit 1, while a second run of the same suite was green — the same intermittent window, now with the typed message. Node kills a process for a rejection nobody holds, which entry 18 records as how a clean shutdown becomes exit 1. So the shim's write roads carry the last-resort handler `Mirror.enqueue` already gives its own chain (`guardDroppedWrites`, `shim/errors.ts`): the rejection still reaches a caller that awaits, and a dropped promise is reported to the error sink at the new phase `write`, which no quarantine counts, rather than floating. The seam cannot know whether a caller held the promise, so it reports every write rejection once — the honest trade against silently swallowing one nobody held.

20. **A write enqueued after the mirror stops refuses, typed (2026-09-24, follow-up round).** The open road entry 19 named. `Mirror.enqueue` closes the queue at teardown and answered a late mutation with a resolved promise that never ran, which left the shutdown window with the worst of both: `Vault.create` and `copy` asked for a row that was never installed and threw `the daemon accepted a write to X but the mirror has no row for it` — the sentence entry 19 exists to remove — while `modify`, `delete` and `rename` went silent. `applyMutation` now checks `stopped` before it enqueues and rejects with **`MirrorStoppedError`**, a subclass of `EngineLostError` rather than a sibling so that every layer already waiting out an absent engine behaves correctly unchanged, while a reader who wants to tell a teardown from a replacement can still ask `instanceof`. For `create` and `copy` it replaces a wrong rejection with a right one rather than adding one; for the other roads it replaces silence. Safe to add only because the write seam's last-resort handler landed with it.

## Reconciliation (2026-09-22) — what shipped differently from the text above

Facts, not doctrine. Each item is something the body of this document asserts about the world that the shipped host does not bear out; the design decision behind it is unchanged unless a ruling above says so.

- **Goal 1 lists `nested-properties` among the tier-1 plugins to "run unmodified and correctly". It does not load.** Its `onload` builds property-editor widgets off `app.metadataTypeManager.registeredTypeWidgets` and asserts each is non-null; this host answers an empty map, the plugin's own assertion fires, and the load is rolled back with its command refused and the vault unchanged. This is a Task 12 decision — the widgets are a GUI rendering surface this host does not have, and inventing one would be inventing behaviour from no capture — and it is **not** a typed `HeadlessUnsupported`, because the plugin's assertion fires before any absent symbol is reached, so nothing lands in the unsupported tally. **The maintainer's verdict on whether to build the surface is open.**
- **Goal 1 also lists `automatic-linker`. It loads and its command runs, and it writes nothing.** `format-file` is gated on both an active file and `getActiveViewOfType(MarkdownView)?.editor`, and this host answers the second with `null` deliberately: a `MarkdownView` would satisfy `instanceof` and then promise a `previewMode` and a `getMode()` that do not exist. **The maintainer accepted this as a documented limit on 2026-09-22; no editor view is provided.** (He had already accepted the `nested-properties` limit above on 2026-09-17.)
- **The Testing section's golden-plugin suite says "byte-level outcomes vs real-Obsidian captures" for the tier-1 list. Three of the eight goldens compare a tree a live Obsidian changed**: `folder-notes`, `obsidian-linter` and `obsidian-rollover-daily-todos`. The other five compare something weaker, each for a stated reason, and `VAULTD-COMPATIBILITY.md`'s Tier 3 section carries the full accounting.
- **The Architecture section's socket paragraph says "a peer-UID check on accept". There is no such check.** The unnumbered plan-level call at the end of the 2026-08-30 corrections already says why — no portable Node API without a native addon — and what replaced it: a `0700` directory, a `0600` socket, and an ownership nonce, with the true cross-UID test as a `sudo`-gated manual check (`server-uid.manual.test.ts`, the suite's one permanent skip). - **The four-way policy table is real and countable.** Measured from the shipped table at commit `8661010`: **269 declared symbols — 104 implemented, 82 safe-stub, 74 absent, 9 harvested** (of the 269, 105 are dotted members owned by their own module rather than barrel exports). Only `escape` is declared: it is the one member the corpus reaches.

## Known limits (2026-09-22) — attribution is ambient over a plugin's awaits

Stated here because it is a property of the design rather than a defect with a fix pending, and because the final review measured it rather than inferring it.

**Which plugin a shim call is recorded against is ambient state**, set by `enterPlugin`/`enterPluginSync` in `shim/policy.ts` and read by the event bus, the dispatch queue, the interaction broker, the write gate, the policy recorder and the quarantine. An asynchronous entry point restores the previous id when its body **returns**, not when the plugin's promise settles, so the window stays open across every `await` inside a plugin's `onload`, command or handler — as wide as the longest wait in it. Three consequences, and the first two are closed:

- **A second plugin never runs inside another's window.** The dispatch queue is a strict FIFO, which is what that guarantees, and it is the only guarantee the FIFO gives.
- **A client operation is pinned to `null`.** `server/ops.ts` dispatches every non-`host.` method inside `enterPlugin(null, …)`, because that road does not go through the queue at all. Before it did, a client's `write_note` sent while a plugin was parked was recorded against that plugin — and since a compatibility probe parks precisely the probed plugin's `onload`, `DryRunGate.dropProbe` then deleted the row from the dry-run transcript an operator reads to decide whether the run is safe to perform for real. Pinned by a test in `test/dry-run.test.ts`. This closes the dangerous direction but opens its mirror image, which is attribution-only and safe: a plugin resuming from its own await while a client operation holds the `null` window reads `null` instead of its own id, and the client window's restore can reinstate a plugin that has already finished — unchanged by design before the host ships.
- **A host-internal callback firing inside a parked window inherits the plugin's id.** A bare timer of the host's own, or an error reported through `shim/globals.ts`'s error sink while a plugin waits, is attributed to that plugin — which can, narrowly, count a host-internal failure toward a parked plugin's quarantine. This one is open, and is the residual.

**`AsyncLocalStorage` is deliberately not the answer, at least not before this host ships.** It is the general fix and it is the wrong size: it would have to wrap every entry point, it costs on every `await` on the hottest path in the host, and a naive context propagation would undo a correctness property this phase established on purpose — `ShimEventBus.tryTrigger` attributes a handler to the plugin that **registered** it rather than to whoever raised the event, which Task 20 found and fixed. Closing the residual is a follow-up with a design behind it, not a wrapper.

**Sync compatibility means running over a folder that Obsidian Sync manages, headless or desktop. `vaultd` never speaks the Sync protocol.**
